
# Security Governance Metrics Framework

## 1. Overview

This document defines the security governance metrics framework developed for the simulated organisation in the ICDFA GRC102 security governance laboratory. The framework provides a structured approach to measuring security control implementation, evaluating effectiveness, monitoring risks and reporting security performance to management and the board.

The framework supports informed decision-making, accountability, regulatory oversight and continuous improvement. The figures generated by the laboratory script are simulated and must not be interpreted as verified results from a real organisation.

## 2. Objectives

The objectives of the framework are to:

- Measure the implementation and effectiveness of security controls.
- Monitor compliance with internal security policies and defined targets.
- Identify weaknesses requiring corrective action.
- Provide management and the board with clear, relevant security information.
- Track security performance over time.
- Establish accountability through assigned metric owners and reporting schedules.

## 3. Security Governance Metrics Categories

### 3.1 Implementation Metrics

Implementation metrics measure the extent to which required security controls have been deployed.

**Patch Compliance**

- Description: Percentage of in-scope systems with required patches installed within the approved timeframe.
- Formula: (Compliant systems / Total in-scope systems) x 100.
- Target: At least 95%.
- Data source: Patch management records and vulnerability scanning reports.
- Owner: IT Operations.
- Frequency: Monthly.

**Security Monitoring Coverage**

- Description: Percentage of critical systems sending security logs to approved monitoring tools.
- Formula: (Critical systems monitored / Total critical systems) x 100.
- Target: At least 95%.
- Data source: SIEM inventory, log sources and monitoring configuration records.
- Owner: Security Operations.
- Frequency: Monthly.

**Policy Compliance**

- Description: Percentage of assessed requirements that comply with approved security policies.
- Formula: (Compliant requirements / Total requirements assessed) x 100.
- Target: At least 95%.
- Data source: Policy assessments, control testing and audit evidence.
- Owner: GRC or Information Security.
- Frequency: Quarterly.

### 3.2 Effectiveness Metrics

Effectiveness metrics evaluate whether security controls achieve their intended outcomes.

**Vulnerability Remediation Time**

- Description: Average number of days required to remediate identified vulnerabilities.
- Formula: Sum of remediation durations / Number of vulnerabilities remediated.
- Target: Seven days or less for the simplified laboratory metric. Actual deadlines should reflect severity, exposure and the organisation's approved remediation policy.
- Data source: Vulnerability scanner and remediation tracking records.
- Owner: Vulnerability Management or IT Operations.
- Frequency: Monthly.

**Security Incidents**

- Description: Number of confirmed security incidents during the reporting period.
- Formula: Count of confirmed incidents recorded during the period.
- Target: Zero incidents as an aspirational target, supported by incident severity and response metrics.
- Data source: Incident management system and security monitoring records.
- Owner: Security Operations.
- Frequency: Monthly.

**Control Effectiveness**

- Description: Percentage of tested controls that operate effectively and have sufficient supporting evidence.
- Formula: (Controls passing effectiveness tests / Total controls tested) x 100.
- Target: At least 95%.
- Data source: Control testing records and internal audit evidence.
- Owner: GRC, Information Security or Internal Audit, according to the control assessment responsibilities.
- Frequency: Quarterly.

### 3.3 Efficiency Metrics

Efficiency metrics assess the resources required to operate the security programme.

**Security Cost per Employee**

- Description: Average security programme expenditure allocated per employee.
- Formula: Total security programme expenditure / Total employees.
- Target: Established through the approved budget and historical comparisons.
- Data source: Finance records, security budgets and HR headcount.
- Owner: Finance and Information Security.
- Frequency: Quarterly.

**Security Staff Ratio**

- Description: Proportion of IT staff dedicated to security responsibilities.
- Formula: Number of security staff / Total IT staff x 100.
- Target: Set according to organisational risk, size and operational needs.
- Data source: HR records and IT organisational structure.
- Owner: HR and IT Management.
- Frequency: Quarterly.

**Security Automation Level**

- Description: Percentage of eligible security processes automated through approved tools.
- Formula: Automated eligible processes / Total eligible processes x 100.
- Target: Defined through the security improvement roadmap.
- Data source: Security tool configuration and process inventories.
- Owner: Security Engineering and IT Operations.
- Frequency: Quarterly.

### 3.4 Impact Metrics

Impact metrics measure the operational and business consequences of security events.

**Security Incident Cost**

- Description: Estimated direct and indirect costs associated with security incidents.
- Formula: Sum of documented incident-related costs during the reporting period.
- Target: Minimise avoidable losses and remain within approved risk tolerances.
- Data source: Incident records, Finance estimates and recovery expenditure.
- Owner: Finance and Information Security.
- Frequency: Quarterly or after significant incidents.

**Business Disruption**

- Description: Total hours of business disruption attributable to security incidents.
- Formula: Sum of documented disruption hours for relevant incidents.
- Target: Remain within approved business continuity and recovery objectives.
- Data source: Incident records, service availability monitoring and business continuity reports.
- Owner: IT Operations and Business Continuity.
- Frequency: Monthly.

**Customer Impact**

- Description: Number of customers affected by a security incident.
- Formula: Count of unique affected customers, based on validated incident records.
- Target: Minimise customer impact and meet applicable notification obligations.
- Data source: Incident investigations, customer records and privacy assessments.
- Owner: Information Security, Legal and the Privacy or Data Protection function.
- Frequency: After significant incidents and in periodic risk reports.

## 4. Metric Definition and Ownership

Each metric should have a documented definition, calculation method, target, data source, owner, reporting frequency and intended audience. Metric owners are responsible for ensuring that source data is reliable, calculations are repeatable and exceptions are escalated.

Targets should be approved by the appropriate management or risk governance body. They should reflect the organisation's risk appetite, regulatory obligations, operational requirements and available resources.

## 5. Reporting Framework

### 5.1 Executive Dashboard

The executive dashboard presents a concise view of the organisation's security posture. It includes key performance indicators, risk and compliance summaries, historical trends and recommendations.

Executives should use this dashboard to identify underperforming controls, prioritise resources and request corrective action. The dashboard should clearly distinguish verified operational data from simulated or estimated values.

### 5.2 Board Report

The board report communicates material security risks, performance against approved targets, significant incidents, compliance concerns and decisions requiring board oversight.

Reporting should focus on business consequences, risk exposure, remediation progress and accountability rather than unnecessary technical detail. Material risks and exceptions should be escalated promptly instead of waiting for the next scheduled report.

### 5.3 Operational Reports

Operational reports provide detailed information for technical teams and control owners. These reports may include individual vulnerabilities, overdue patches, monitoring gaps, incident response actions, failed control tests and remediation deadlines.

Each significant finding should have an assigned owner, priority, due date and recorded remediation status.

## 6. Metrics Lifecycle

The framework follows six stages:

1. **Define:** Select metrics aligned with security objectives, organisational risks and compliance requirements.
2. **Collect:** Obtain data from approved and documented sources.
3. **Validate and calculate:** Check data quality, apply consistent formulas and document assumptions.
4. **Analyse and report:** Compare results against targets, identify trends and communicate findings to the appropriate stakeholders.
5. **Act:** Assign corrective actions, allocate resources and escalate material risks.
6. **Review:** Assess whether metrics remain relevant and update definitions, targets and reporting arrangements when necessary.

## 7. Status Indicators and Escalation

The dashboard uses status indicators to help stakeholders interpret results:

- **Green:** The metric meets the approved target.
- **Amber:** The metric is approaching a threshold or requires management attention.
- **Red:** The metric materially misses its target or indicates an unacceptable risk.

For metrics where higher values are better, such as patch compliance, performance should be compared with the minimum target. For metrics where lower values are better, such as remediation time, performance should be compared with the maximum acceptable duration.

A zero incident count must not automatically be interpreted as proof of effective security. It should be considered alongside monitoring coverage, reporting quality and other evidence.

Material control failures, overdue high-risk remediation actions and potential regulatory breaches should be escalated according to the organisation's approved incident and risk escalation procedures.

## 8. Data Quality and Limitations

Reliable governance reporting depends on complete, accurate, consistent and timely source data. Metric owners should validate source records, document missing data and retain evidence supporting reported values.

The laboratory script generates simulated historical data using random values and contains predefined dashboard figures. Its charts demonstrate how trends and targets can be presented; they do not establish actual security performance or prove that controls are effective. In a production environment, the simulated values must be replaced with validated data from operational systems.

## 9. Continuous Improvement

The framework should be reviewed periodically to ensure that metrics remain aligned with business objectives, changing threats, regulatory requirements and the organisation's risk profile.

Reviews should consider whether targets remain appropriate, whether reporting leads to meaningful action, whether data sources are reliable and whether additional metrics are needed. Metrics that no longer support decision-making should be revised or retired.

## 10. Conclusion

This security governance metrics framework provides a consistent approach to measuring security control implementation, effectiveness, efficiency and business impact. The executive dashboard, board report and operational reporting process translate security information into actionable oversight.

By assigning ownership, defining targets, validating evidence, escalating exceptions and reviewing performance regularly, the organisation can strengthen accountability, support risk-informed decisions and drive continuous improvement in its security governance programme.
